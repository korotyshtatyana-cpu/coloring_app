# Flutter Good Practices & Coding Standards

Для поддержания высокого качества кода, его читаемости и производительности в проекте "Раскраска PRO" устанавливаются следующие правила.

## 1. Архитектура и Структура (Clean Architecture)

- **1 класс — 1 файл**: Каждый класс должен находиться в отдельном файле. Исключение: `StatefulWidget` и его `State` всегда в одном файле.
- **Разделение ответственности**: Бизнес-логика только в BLoC и UseCases. Виджеты отвечают только за отображение.
- **Инъекция зависимостей**: Все внешние зависимости передаются через конструктор. Используйте `appLocator` (get_it) только в точках входа (экран, инициализация).

## 2. Разработка Виджетов

- **Композиция вместо наследования**: Разбивайте сложные виджеты на мелкие переиспользуемые части.
- **Запрет на методы `_build...()`**: Не создавайте методы, возвращающие `Widget`. 
    - Если UI сложный — создайте новый `StatelessWidget`.
    - Если UI простой и используется один раз — пишите в `build`.
    - Если UI повторяется внутри одного `build` — вынесите в локальную переменную (например, `final spacer = const SizedBox(height: 16);`).
- **Const везде, где возможно**: Используйте `const` конструкторы для уменьшения количества перерисовок.
- **Специфичные виджеты**: Используйте `SizedBox` вместо `Container` для пустых отступов.

## 3. Состояние и Логика (BLoC)

- **Семантика событий**: Называйте события как действия пользователя или системные факты (например, `ChangeColor` вместо `SetColor`).
- **Специфичные `select`**: В виджетах используйте `context.select((Bloc b) => b.state.property)` вместо `watch`, чтобы избежать лишних перерисовок при изменении неактуальных свойств состояния.
- **Immutable State**: Состояние всегда должно быть неизменяемым (используйте `copyWith`).

## 4. Оптимизация и Производительность

- **Избегайте глубокой вложенности**: Если дерево виджетов уходит глубже 5-7 уровней — это сигнал к выделению нового виджета.
- **Ресурсоемкие операции**: Никогда не делайте вычисления или запросы к API внутри метода `build`.
- **Локальные переменные**: Если значение (цвет, стиль, условие) используется в `build` более одного раза — выносите его в переменную в начале метода.
- **RepaintBoundary**: Используйте для изоляции сложных областей отрисовки (например, холст для рисования).

## 5. Стиль Кода и Именование

- **Декларативный UI**: Метод `build` должен читаться как структура, а не как алгоритм. Выносите логику обработки нажатий в отдельные именованные методы (например, `_onColorSelected`).
- **Локализация**: Никогда не используйте хардкод строк. Только `LocaleKeys.some_key.tr()`.
- **Темы**: Используйте `AppColors.of(context)` и `AppFonts`, избегайте прямого обращения к `Colors.black` (если это не прописано в правилах дизайна).
- **Размер строки**: Ограничение 100 символов.

## 6. Рефакторинг (Чек-лист)

Перед завершением задачи проверьте код:
1. [ ] Нет ли дублирующегося UI?
2. [ ] Все ли виджеты вынесены в файлы?
3. [ ] Используются ли `const` конструкторы?
4. [ ] Нет ли логики в `build`?
5. [ ] Корректно ли работает `context.select`?
